# ValoLineup

ValoLineup 是一个纯静态的《无畏契约》Lineup 图鉴。地图、英雄和点位内容来自仓库中的 YAML，构建时生成浏览器数据；运行中的页面不依赖服务端接口。

## 本地运行

环境要求：Node.js 22.13 或更高版本（推荐使用仓库 `.nvmrc` 指定的 24.18.0）和 pnpm 11.10.0。

```bash
nvm use 24.18.0
pnpm install
pnpm run dev
```

生产静态文件输出到 `dist/`：

```bash
pnpm run build
```

Vite 使用相对资源路径，`dist/` 可以作为完整静态目录交给 Toy CLI 预览和发布。

## 编辑 Lineup

当前已导入 r6 编辑包：共 32 个点位、68 张点位图片。浏览器可修改名称、进攻/防守阵营、区域、说明和视频，也可删除点位/图片。新建点位默认继承当前攻守视角，区域提供 A/B 点（适用地图含 C 点）快捷选择，同时支持自由输入。

图片上传后先在浏览器转换为 WebP（保留分辨率，质量 86%），仅压缩后的文件进入草稿与 IndexedDB；不保留 PNG/JPG 原图。已有 WebP 不反复有损编码。编辑区实时显示本编辑包的图片用量 / 128 MiB，单张原图与压缩后均不得超过 12 MiB；超限会阻止保存和导出。点位修改后，该点位的全部图片都会计入包体。

粘贴请先复制图片，再点击显眼的“选中…区域以粘贴”按钮，按 Ctrl+V（macOS 为 ⌘V）。不再使用可能被 Toy 容器权限策略禁用的 `navigator.clipboard.read()`；上传文件入口仍保留。

页面中的“编辑点位”先通过 Toy SDK 获取当前用户资料，再基于当前可见点位创建草稿。可以拖动点位、添加或粘贴站位图、瞄点图和效果图，也可以新增 Lineup 并填写地图、英雄、技能与可选的 B站 BV 号。页面不会直接修改仓库。SDK 未加载、用户取消授权或环境不支持时不会进入编辑模式；本地开发调试身份流程需模拟 SDK，真实授权需在 Toy 中验证。

“保存编辑”将一个持续编辑的图层保存在 localStorage，图片保存在 IndexedDB；刷新后查看态也会显示修改，并提供“导出编辑包”。继续编辑会沿用同一个包 ID，保留首次修改前的快照。修改后再次保存增加修订号，不新增另一个更新包。

“导出编辑包”下载 `valo-lineup-edits-<包ID>-r<修订号>.zip`，包含累计变更和这些点位用到的全部图片。导出不等于保存，也不会清空或退出草稿。退出编辑每次均提示确认，只放弃尚未保存的变更；此前已保存的编辑保留。刷新或关闭前应先保存或导出。

## 上传者与浏览器更新历史

每个 Lineup 沿用唯一 ID，新增时生成随机 ID。现有 26 个点位的上传者为 PeterAlbus / B站 UID `2003822`，点击可打开其主页。新点位记录 `getUserProfile()` 返回的昵称和可选 `toyOpenId`；SDK 不返回 UID/MID，不推测或补填 UID，因此新用户没有主页跳转按钮。修改已有点位保留原上传者，更新包作者记录本次编辑人。昵称和包作者均不是可信签名，不能用于权限校验。

“更新历史”页面提供：

- 顶部的本地编辑状态、下载和删除编辑功能。
- 浏览器更新包 ZIP 导入、删除、上移/下移；同包 ID 重复导入在原位置替换，不重复堆叠。
- 仓库永久更新的更新人、应用时间、实际更新地图和点位数量。

客户端始终按 **仓库点位 → 从上到下的浏览器更新包 → 已保存手动编辑** 合并。浏览器不检查修改前快照，相同 ID 完整覆盖；没有对应原点位的修改也直接加入。共享落点成员被局部覆盖后，以各自实际坐标显示，不产生仓库式冲突。

浏览器包与手动编辑的清单存放在 localStorage，图片按 SHA-256 存在 IndexedDB。同名不同内容图片按获胜图层分别解析；删除一个包不影响其他包或本地编辑所需图片。存储按部署路径隔离，不跨浏览器/设备同步。浏览器清理网站数据、隐私模式结束或存储回收都可能导致数据丢失，重要编辑请下载 ZIP 备份。空间不足时保留当前草稿和上一次已保存的数据。多标签页写入有锁和版本检测；出现过期提示应先导出草稿再刷新。

## 导入编辑包

开发者拿到 ZIP 后，在最新仓库内容上运行：

```bash
pnpm run content:import-edits -- /absolute/path/to/valo-lineup-edits-YYYYMMDD-HHmmss.zip
```

CLI 和浏览器均接受 v4、v5 更新包，不兼容更早的 v3 包。普通新增/修改仍导出 v4；有删除操作时导出 v5，避免旧客户端无声忽略删除。v4 基线样例保持不变。协议见 [v4 基线](docs/edit-package-v4.md) 和 [WebP / v5 兼容扩展](docs/edit-package-v5.md)。CLI 会把编辑包逐条合并到当前仓库。不同用户基于同一版本编辑不同 Lineup 时，各自的包可以按任意顺序导入。它会校验：

- 编辑包格式；
- 地图、英雄、技能和点位引用；
- 每条已有 Lineup 的修改前后快照；
- 图片路径、格式、大小和 SHA-256；
- B站视频字段是否为完整 BV 号。

新增 Lineup 使用随机唯一 ID，会直接合并。修改已有 Lineup 时，仓库记录与编辑包的修改前快照一致才会应用；如果仓库记录已经变化，该 Lineup 会被列为冲突并跳过，包里的其他新增和无冲突修改仍会继续导入。重复导入同一个包时，已经等于修改后快照的 Lineup 会被识别为已应用。

CLI 会在终端逐条列出跳过的冲突及原因。共享同一个地图落点的多种方法共用一组坐标；如果该组中出现并发冲突，相关坐标修改会作为同一个落点整体跳过，避免地图上的同组方法产生不一致坐标。

删除同样使用 `before` 检测仓库冲突；浏览器端无条件删除对应 ID。新建后又删除的点位会取消新增，不输出多余删除操作。后面的更新包可以重新加入被较早包删除的点位，本地手动删除仍在最后生效。

旧 v4 包中的 PNG/JPG 会先校验，再转成 WebP 后保存。`content/image-migrations.json` 与图片的 `original` 元数据仅记录旧路径和校验值，不存原图，用于跨压缩版本匹配 `before` 快照。已有浏览器资料也会在启动时整体迁移，保持包 ID、修订号和顺序；迁移失败保留旧数据。重要数据仍建议导出 ZIP 备份。

可应用内容全部通过校验后，CLI 才会更新 `content/lineups.yaml`、写入 `public/lineups/` 图片、追加 `content/history.json` 并重新生成 `src/data/content.json`。历史记录仅统计实际应用成功的点位，重复导入或全部冲突时不新增历史。包内已有同名图片仅在 SHA-256 相同时复用，不覆盖仓库不同内容的图片。若校验或构建失败，本次点位、图片及历史变更会一起回滚。

基于其他浏览器更新包编辑并导出的包，其 `before` 快照可能依赖那些更新包。交给仓库时需先导入其基础包；浏览器端不受此限制。

## 内容维护命令

```bash
pnpm run content:build
pnpm run content:import -- /absolute/path/to/lineups.md
pnpm run content:import-agents -- /path/PublicContentCatalog.json /path/catalog-assets
pnpm test
pnpm run lint
pnpm run test:browser
```

`content:import` 是保留的单次 Markdown 导入口；正常开发和构建只读取 `content/*.yaml`，不会重新导入 Markdown。

`test:browser` 使用独立测试浏览器，会重置测试站点的本地数据。先启动 `pnpm run dev --host 127.0.0.1 --port 4174 --strictPort`，再以独立临时用户目录启动 Chromium/Edge，设置 `--remote-debugging-port=9335` 并打开该地址。不要对日常使用的浏览器运行测试。浏览器测试用 SDK 模拟资料，不会登录真实账号。
