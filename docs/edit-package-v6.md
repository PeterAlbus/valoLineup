# v6：图片引用与逐点位导入

v4/v5 的包结构、完整图片读取能力及冻结 v4 样例保持不变。需要省略已有图片时使用 v6，不能在 v4/v5 下悄悄省略文件。旧客户端会明确拒绝 v6；新客户端同时支持 v4/v5/v6。没有图片引用的导出仍按是否含删除操作使用 v4/v5。

## 图片声明

v6 保留完整的 `changes`、`before`、`after`、点位 ID、包 ID 和修订号语义，仅新增可选字段：

```ts
referencedAssets?: Asset[];
```

`Asset` 与 `uploadedAssets` 的声明结构相同：`key`、`lineupId`、`kind`、`alt`、`mimeType`、`size`、`sha256`，以及允许的附加元数据。

- `uploadedAssets`：ZIP 必须携带对应路径的图片字节。
- `referencedAssets`：引用已有 WebP 图片，ZIP 不携带其字节。接收方从 IndexedDB 或部署目录／仓库的 `public/<key>` 读取，核对文件签名、大小及 SHA-256，不能仅凭路径认为图片相同。
- 两组声明的并集必须恰好覆盖所有新增／更新后的图片引用；不能遗漏、重复、混用所属点位或篡改说明。删除操作不需要 before 图片。
- 两组声明总计最多 500 张；单张仍不超过 12 MiB。128 MiB 图片容量只计算实际随包携带的图片；ZIP 文件及清单的原有限制继续生效。
- 包的未知附加字段继续保留。未来扩展不能改变上述字段含义，或让旧包缺少新的可选字段时无法导入。

## 导出规则

构建数据在原 `mediaBytes` 旁新增 `mediaAssets`，按图片路径记录大小、MIME 和 SHA-256。导出比对实际图片与内置图片，以及其他已应用本地包中的图片：路径、字节摘要、大小、格式全部一致时，改为引用；否则携带图片文件。同路径不同内容不能误判为“未修改”。来自其他本地更新包的图片也遵守这一规则，不再强制重复携带。

手动编辑层不作为自己的外部依赖，所以本轮新上传的图片在保存、继续编辑及重复导出时仍需携带。持续编辑沿用原包 ID 和累计修改，不拆出新包。只改名称、阵营、坐标、说明或图片排序／说明时，未变化的图片不再重复压入 ZIP。

保存过的旧 v4/v5 完整包，导出时也会重新判断哪些图片可以引用。删除来源包或应用升级后，如果图片不再存在于内置／其他包中，但已在手动编辑的缓存中，下一次导出会自动恢复携带这些图片。

编辑页“随包图片”显示实际需携带的图片字节，不等于 IndexedDB 的总存储占用。历史页区分随包大小和引用图片数量。

## 导入及局部失败

浏览器和仓库都先验证包结构，再逐个点位验证所需图片。某个点位的引用图片不可用，或 ZIP 图片缺失、大小／签名／摘要不符时，跳过该点位及其全部图片，继续处理其他点位。清单格式错误、非法路径、ZIP 结构损坏等仍拒绝整个包。

- 浏览器：不检查 before 快照，成功点位仍无条件覆盖；失败点位保留原内容。重新导入同 ID 包的新修订时，保留旧修订中失败点位的操作及图片，不能因为部分替换而回退或丢失这些点位。
- 仓库：成功通过图片检查的点位继续执行原有 before 冲突和共享落点一致性检查；缺图不会阻断其他独立点位。图片失败、快照冲突分别在输出中列出；历史仅记录实际应用成功的点位。
- 所有点位都因图片失败时，不保存空包、不替换旧包、不新增仓库历史，直接报告没有可导入的点位。
- 导入结果会列出失败点位、图片路径和原因。补齐来源更新包或同步部署／仓库后，可以重新导入原 ZIP；已成功的仓库点位仍按幂等规则识别。

浏览器只将成功点位的完整图片（包括已解析的引用）保存在 IndexedDB；引用不是运行时依赖链。以后删除来源包、调整顺序或刷新，不会破坏已经成功导入的图片。localStorage 键、IndexedDB 名称及版本保持不变，继续使用原事务提交与回收规则。

这意味着精简包不是独立的全图片备份。分享或迁移到新浏览器时，应同时保留来源更新包；缺少依赖图片只会阻止对应点位导入，不会阻止整个更新包。

## 回归保障

`check-image-references.mjs` 使用独立点位和生成图片，覆盖零图片导出、混合引用／上传、本地包复用、同路径不同内容、v4 兼容、非法引用、缺图／损坏逐点位跳过、旧修订保留、CLI 历史与补图重试。

`check-image-references-browser.mjs` 验证真实页面的零图片 ZIP／容量、旧保存编辑重新导出、引用图片刷新缓存、部分导入、失败点位旧版本保留、导入来源包后重试，以及删除来源包后的图片完整性。
